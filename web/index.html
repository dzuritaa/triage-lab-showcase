Root cause direction

Check the outbound integration job logs and API/SFTP credentials to the bank; verify the transfer attempt succeeded or failed, and whether authentication or connectivity is the blocker.

Drafted first response

We see the file generated at 20:00 but did not reach the bank. We need to check the transfer job logs immediately to see whether the send attempt failed and why. Can you provide: (1) the exact filename and size of the file in the outbound folder, (2) whether your bank credential or API key for this payment file transfer has been rotated or renewed recently, and (3) access to the integration job logs covering 20:00–21:30 last night. If the transfer failed due to credential expiry or rotation (similar to INC-1003), we may need to refresh those with the bank and retry. We're treating this as blocking and will prioritize the log review now.

How it was measured

Ten held-out tickets written so they share no phrasing with the corpus they are scored against. One command produces the table below, and that same command runs on every pull request. It needs no key and no network, so a pull request from a stranger's fork gets scored exactly like one of mine.

Retrieval recall @3 9 of 10 cases random baseline: 23%
Retrieval recall @1 6 of 10 cases random baseline: 8%
Category accuracy 6 of 10 cases majority-class baseline: 20%
Priority accuracy 7 of 10 cases majority-class baseline: 40%

Priority scores highest and deserves the least credit for it. Eight of the ten held-out cases are P2 or P3, so a four-way label behaves like a two-way one, and a ticket whose symptom resembles a past incident usually carries a similar impact. The 70% is the bar the model has to clear, not a result to be pleased with.

Every number in this section comes out of python -m evals.run. Regression floors sit about ten points below measured performance, so ordinary variation will not break the build but a real drop will. An earlier floor was set at 70% before anything had been measured, above anything the system had ever achieved, which would have left the build permanently red.

The case it gets wrong

Recall@3 of 90% flatters the retriever. The honest reading is in the tenth case, so here it is.

Retrieval failed
CASE EVAL‑02

A contractor cannot open the finance application

P1 4h
P2 8h · urgent
P3 24h
P4 72h

The audit starts at 9am tomorrow and he has three days on site. The right documents are about security group membership. The retriever returned branch-office network slowness, then an unrelated login loop, then the change freeze calendar.

What the reporter wrote “cannot open the finance application”
What the answer says “the logon script maps only the drives the account already has rights to”

Same problem, two vocabularies, almost no shared words. A lexical matcher cannot cross that gap by construction; no amount of tuning fixes it. This single case is the clearest argument for adding embeddings, and it is why the next phase measures them before adopting them.

Handed three irrelevant documents, the model still returned the correct category and priority and pointed at group membership, which is the content of the article it was never shown. The system degrades gracefully. It also means recall@3 overstates how much retrieval currently contributes.

Why there is no vector database

File copy

Twenty-five documents. BM25 in about 150 lines of standard-library Python finds the right incident in nine cases out of ten, where drawing three documents at random would find it in two. No second vendor. No key to leak, no index to keep warm, no monthly bill.

That decision carries a stated expiry. It reverses if the corpus passes roughly 5,000 documents, if recall@1 starts mattering more than recall@3, or if an embedding adapter beats these numbers by enough to justify the cost. The evidence is written down alongside the case against it.
